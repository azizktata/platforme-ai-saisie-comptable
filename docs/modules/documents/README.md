# Documents facture et workflow IA (Phases 3–5)

Le module Documents est intégré au workspace Factures. `InvoiceController` gère l’intake privé, l’historique, l’aperçu/téléchargement protégé, le détail à la demande, les statistiques d’état, la correction d’extraction, la relance individuelle et l’action groupée des seuls statuts éligibles. `ProcessInvoiceOcr`, `ExtractInvoiceData` et `AnalyzeAccountingProposal` sont des jobs tenant-scoped sur la file `ocr`.

La liste `/invoices` ouvre la page dédiée `/companies/{company}/invoices/{invoice}`. Elle contient l’import par glisser-déposer, `Tout analyser`, compteurs, état et colonnes document/fournisseur/numéro/date/TTC/confiance de proposition. L’utilisateur peut également télécharger un PDF fictif d’exemple ou l’ajouter volontairement à la sélection avant de confirmer l’import ; il n’est jamais créé comme facture sans action. Les imports réels et l’exemple passent ensuite par le même workflow automatique.

La page détail est à deux colonnes : `InvoiceDocumentViewer` et un résumé extrait/financier sont à gauche ; `InvoiceReviewPanel` forme l’espace IA/comptabilité à droite. Le viewer montre l’original PDF/image avec zoom, ajustement, rotation des images, plein écran et navigation PDF ; la rotation PDF native dépend du navigateur. Le workspace commence par une carte de confiance globale et des barres de confiance fournisseur/montants/TVA/type/compte. Seuls les scores réels des lignes comptables sont disponibles aujourd’hui ; les dimensions sans score sont affichées `N/D`. Cinq cartes ordonnées présentent les données modifiables, le type de facture, la proposition brouillon éditable, les contrôles verticaux et la décision humaine. Sur petits écrans, les deux colonnes s’empilent ; les panneaux défilent séparément sur desktop.

OCR.space Free Engine 3 est le défaut. La transcription est conservée dans `ocr_text`, séparément de `ocr_response`. L’extraction structurée par OpenRouter utilise le modèle configurable `qwen/qwen-2.5-7b-instruct:free` par défaut ; le JSON Schema est strict et Laravel normalise/valide les résultats. La sortie attend uniquement le JSON et ne contient aucun raisonnement, explication ou calcul. Les appels OCR, extraction et proposition utilisent des configurations distinctes. Mistral reste sélectionnable pour fournir directement les données structurées ; les propositions comptables utilisent toujours le modèle séparé `openrouter/free`.

Une relance d’extraction utilise le `ocr_text` déjà enregistré et ne redispatche pas OCR. Les réponses mal formées, hors schéma ou safety-classifier sont refusées ; les extractions précédentes valides restent intactes en cas d’échec. Le recalcul des montants est une action déterministe explicite, locale et sans LLM : elle utilise le HT imprimé sans déduire une seconde fois la remise séparée, puis ajoute TVA + FODEC + autres taxes + timbre pour le TTC brut et déduit la retenue uniquement pour le net à payer ; les taxes vides exigent confirmation avant d’être considérées nulles. Le type de dépense est enregistré avec la proposition et s’appuie sur l’activité/secteur réels de la société. Le gestionnaire peut modifier les lignes, régénérer les brouillons éligibles, rejeter sans écriture, valider explicitement ou télécharger un CSV interne. Les contrôles distinguent passé/avertissement/bloquant/en attente/indisponible ; année fiscale et dédoublonnage de numéro ne sont pas déclarés vérifiés. Le CSV n’est pas une intégration Sage ; les gardes de devises et permissions restent côté serveur. Les utilisateurs société en lecture seule peuvent consulter, mais pas modifier.

Routes, configuration complète, statuts, contrôles et tests : [`../invoice-processing/README.md`](../invoice-processing/README.md). Exigences : [`PRD.md`](PRD.md). Les originaux restent privés ; aperçu/détails vérifient systématiquement l’accès à la société. Aucun appel fournisseur ne vient du navigateur.
